# Low-memory connected-app polish

Version 17 / 2.3.0-beta2 coordinates with TypeRight 222. It supersedes the unpublished version 16 draft. External polish previously skipped the chat path's RAM-based model selection and could reuse the Primary's larger context settings after switching to a Secondary. Startup/model replacement also returned only the legacy BUSY status, which TypeRight treated as an immediate failure.

The update introduces text-free, explicitly requested model preparation. Approved clients share one load job. BI checks current available RAM and its reserve, chooses a fitting context/model, confirms actual activation and exposes a safe loading/activity state. A fitting already-loaded fallback remains active for subsequent short polish requests. The actual Binder generation uses the admitted context. Model files, shared CPU/GPU memory accounting, backend selection and inference ownership remain managed by BI.

A rejected RAM decision retains the candidate only for its explanation. Version 17 returns that decision before any activation attempt. A repository-level regression with a catalog E4B primary, 3 GB free RAM and an absent model file reproduced PREPARATION_FAILED before the fix and now passes with LOW_MEMORY, no active model and no file-load attempt.

No AIDL transaction, runtime dependency, download policy or client approval rule changes. The Binder permission/action now derive from the installed application ID, matching the manifest; production names are unchanged and isolated validation uses its own permission. Existing API v2 clients remain compatible. Status polling never triggers a model load or inference. Preparation carries no editor text, and errors do not expose native exception strings or paths. Concurrent clients share preparation but still compete for the existing single inference slot; text is not queued behind another application's request.

See [the API contract](../APP_INTEGRATION.md) for new optional Bundle fields. New tests cover a shared load, startup/active-inference exclusion, failed and low-memory preparation, explicit retry, role/context handoff and compatible startup metadata.

Validation on 27 October 2026: **171 unit/Robolectric tests passed**, zero failures/errors/skips; debug/test APKs, release lint and signed production bundle passed. [GitHub Android checks](https://github.com/sidhrthmnn/BetterIntelligence/actions/runs/40522549778) passed for product source `cb18299`, including real ARM64 CPU/Vulkan compilation. No new GPU benchmark is claimed. See [build records](beta2-build-validation.json).

The HONOR was connected for genuine weight staging, SHA-256 verification and fixture setup. At the final setup it reported **3156 MB available**, **2644 MB safe model budget**, with estimated requirements of **3590 MB for Gemma E4B** and **1801 MB for Qwen 1.7B**. No pressure was simulated and the larger model was not forced into memory. The phone then disconnected from ADB before the final cross-process TypeRight UI/polish checks. Those checks and test-app cleanup are **pending reconnection**, and no successful physical polish is claimed for this update. Production apps/data were not replaced.

The release candidate remains held for that requested device check. Its bundle is version 17 / 2.3.0-beta2, 90,398,363 bytes, SHA-256 `2882db20a6a753b492d561d9801699778deb2d5d1baeee35f8ccaf45b60fe68a`. Bundletool and upload-signature verification passed; API 24 minimum / 36 target and the two native ABIs are retained. The unpublished version 16 draft is superseded.

Limits: fallback model quality and supported input size still vary. Memory estimates are admission checks, not a guarantee against all system pressure. An operation can fail if resources change after readiness. TypeRight reports these failures and preserves the original editor text. Preparation may finish after a consumer stops waiting, but cancelled editor text is never sent automatically afterward. No battery, GPU/NPU speed or universal model-quality improvement is claimed by this reliability update.
